# Security model

Shade assumes the repository and its dependency metadata can be malicious.

What that does **not** cover: Shade does not sanitize committed content or
repository history. A credential a repository already carries in a test
fixture, a document, an `.env.example` or a CI file is the owner's decision;
Shade records what it found and opens the repository. Shade's secret machinery
exists to keep *untracked private files* out of Git, checkpoints and
publishes.

## Git and filesystem

- Fetch/import first receive into a daemon-owned `0700` quarantine, validate every reachable commit tree, and only then promote through explicit fully-qualified refspecs; `refs/shade/*` never participates. The base commit's tree is held to the full checkout policy; its ancestors are checked only for the features Shade cannot materialize at all.
- Managed imports contain their own objects and have no permanent alternates or hardlinks.
- Submodules, Git LFS, custom filters, tracked private `.env` files and tracked dependency output are rejected before checkout/checkpoint, and every one of those rejections names the first offending path in the response `next` (`untrack apps/web/.env.production, then retry`), never any content, bounded so the error stays inside the common response budget. `.env.example` and the other template names below are ordinary tracked content. Gitlinks, `.gitmodules`, LFS pointers, `.lfsconfig` and filter-declaring `.gitattributes` are refused wherever they are reachable; a private `.env*` name or a `node_modules` path that exists only in an ancestor commit is not, because nothing is ever checked out from it.
- Managed worktrees install required internal Git filters. The persistent content filter scans the complete request before returning any bytes to Git, with an anonymous private spill file for inputs above 1 MiB. Ordinary porcelain, including `git add -f`, fails before Git writes a detected secret blob. Policy applies to the clean direction, which is the one that decides what enters Git; a smudge request returns bytes the object database already holds, so it passes through unchanged. That direction scans new content only: a request whose bytes hash to the object Git already records for the same path is admitted without a scan, because Git re-cleans tracked paths whenever an index loses its stat cache and admitting them writes no object the repository does not already contain. Safe bytes pass unchanged in both directions.
- `context` is an observational fast path: one porcelain-v2 status call reports HEAD and change counts without a full policy inventory. Every retention or integration boundary—checkpoint, fork, sync, resolution, publish, release and GC—performs the fail-closed inventory before it can create an object/ref or move a branch.
- Production materialization requires successful APFS clone syscalls on the same filesystem. There is no copy fallback.
- Whole-directory cloning is restricted to verified, immutable daemon-owned bases/layers with at most 25,000 inventoried entries and no internal hardlinks. Agent-owned workspaces always use controlled traversal. Symlinks remain symlinks, special filesystem objects are rejected before cloning, and destination publication never replaces an existing tree.
- Worktrees are detached and locked. Synthetic checkpoint objects are private retention anchors, not remote branches.

## Dependencies

Shade uses exact host tool paths, versions and executable digests but never installs a toolchain. Fingerprints omit absolute paths and credentials. JavaScript installers run frozen with scripts disabled; Python accepts only hashed wheels under `uv.lock` and never installs the project; Cargo and Go only populate/verify their native download caches. Every provider performs an online fill followed by an offline replay where applicable. Replay runs through macOS `sandbox-exec` with network operations denied for the process tree. A failure to apply isolation fails preparation. Bun uses that OS guarantee because its install CLI has no offline flag; the other providers also keep their native offline flags.

Executable configuration, missing/stale locks, Python source builds, VCS/path/editable Python sources, dependency-added Python startup code, unapproved JS lifecycle scripts, `build.rs`, proc macros and Go build/generate actions are either statically rejected or never invoked by Shade. Python preparation first creates an empty environment with the pinned uv/interpreter, records its bootstrap files, and rejects any changed bootstrap file or additional startup hook after wheel installation.

TOML, YAML and JSONC locks/configuration are inspected structurally. Corepack proxies resolve only to already installed matching packages. npm/pnpm run with their exact Node interpreter; receipts include interpreter identity. Runtime provisioning declarations and executable hooks are rejected. pnpm retains its separate metadata and policy-verification cache between online fill and offline replay; security policies remain enabled.

The [configuration boundary](DEPENDENCY-CONFIGURATION.md) also isolates external npm/uv/Cargo configuration during preparation. Python requires stable uv >=0.11.16 and disables executable keyring providers. Cargo's sandbox hides parent/native-cache configuration and pins rustc. Go parses local workspace/replacement declarations with its own read-only JSON commands inside the COW probe and rejects paths outside it.

JavaScript lifecycle consent lives in the daemon database and is bound to provider/package/version/integrity. Repository metadata cannot grant it. Approval and revocation commit with the operation result and outbox; decisions apply to new preparations, while current workspaces retain their bytes. Approved hooks run on COW build stages with pinned Node/shell, network denied and writes limited to their package and isolated temporary directories. Existing hardlinks are detached; nested dependencies remain protected. The dependency graph determines hook order. pnpm installation paths are resolved from the locked importers/snapshots, including aliases and peer variants; graph paths and dependency names are validated before invoking a manager. Root/workspace hooks never enter a reusable artifact. See [script approvals](SCRIPT-APPROVALS.md) for commands and scope.

## Secrets

Shade rejects trees containing a path whose basename starts with `.env`, including `.envrc` and `.environment`. One family of names is excepted: a basename whose final dot-suffix is `example`, `sample`, `template`, `dist` or `defaults` is a committed placeholder, so `.env.example` and `.env.local.example` pass as ordinary tracked content while `.env`, `.env.local` and `.env.example.local` do not. The suffix list is matched byte for byte. The required clean filter refuses every other `.env` name, and any content the detector recognizes, before Git writes its blob.

A content match in a blob that is *already tracked* is not a rejection. Refusing it would refuse the repository for a credential its owner committed long ago, which Shade cannot unsay and which is visible to everyone who can clone the project; real repositories carry private-key headers inside redaction tests and credential-shaped URLs inside `.env.example` and CI files. What the base tree carries is instead surveyed once, when that base is first admitted: the count and the matching paths are recorded as a `repository.tracked_secret_matches` event and counted by `shade doctor` as `tracked_secret_matches`. The record contains paths only -- never a fragment of the matching bytes.

The clean filter asks that same question per request. When the scanner matches, the filter computes the object ID Git would give the bytes in front of it -- in the repository's own object format -- and compares it with what Git records for that path: the entry in the index the running command reads, or the path in HEAD when the index has none. Identical bytes are passed through; anything else is refused exactly as before, so an untracked private key and a change that introduces a credential into a tracked file are both still withheld. This is what lets a repository whose committed source matches the detector keep its lifecycle: staging a checkpoint through a private index read out of a tree, verifying a materialized base, and rewriting a woken successor's index all make Git re-clean paths whose bytes it stored long ago, and a woken session could not otherwise come back at all. Both listings are read at most once per filter process and only after a match, so a repository that carries nothing detectable runs no extra command. The private `.env*` names are never rescued this way: the `shade-secret` driver refuses them whatever they contain, and so does the content filter for the template names routed to it.

The detector recognizes private-key headers, selected GitHub/Slack/Google/Stripe/OpenAI token formats, credential-bearing URLs and sufficiently varied credential assignment literals. Detection is heuristic; it does not recognize every possible credential. The same scanner handles binary data and signatures spanning read boundaries, returning only a decision.

Fetch/import validate all reachable history in a private quarantine; checkpoint and publish revalidate HEAD, the real index and the candidate working tree before creating private refs or moving a branch. Checkpoint tree creation uses a private index snapshot whose paths and blobs are validated before `write-tree`, so concurrent Git index replacement cannot bypass that check. Current private working files are excluded from checkpoint staging and copied separately into forks/successors with `0600` permissions, including when a tracked file's safe Git version differs from its private working contents. Read-only status bypasses the content filter so it can report those changes without writing blobs.

Sleeping a workspace vaults its current private working files beside those baselines under the same `0700` directories with `0600` files, staged and published by one atomic directory swap (`renamex_np(RENAME_SWAP)`) whose parent directories are then fsynced, so a re-slept workspace is never briefly left with no vault and a power cut cannot lose the entry; the vault is restored only into that workspace's own successor on wake, and is removed with the workspace it belongs to. Baselines live under the private Shade root with mode `0600`; their files occupy a separate directory from the manifest, so arbitrary private filenames cannot replace metadata. Directories and the socket are user-only. Review payloads contain only relative filenames, key names and one of `parent`, `child`, `unchanged`, `removed` or `conflict`. Values, fragments and hashes never enter public responses or logs. Dotenv merging preserves comments and assignment formatting. JSON objects and TOML tables merge recursively, with JSON Pointer key paths in previews; scalar/array edits and deletion conflicts remain explicit. One-sided changes preserve exact bytes. Opaque/binary files support keep/discard and one-sided merges; divergent edits remain pending before a successor is allocated. A merge writes a successor; it never edits an active parent.

GC performs secret discovery even for a workspace whose lease has already been released. Changes requiring review produce a `review.required` event containing the key-only preview and block deletion. Keep/discard decisions and their operation outcomes commit atomically; reviewed merges commit their handoff atomically. Review resolution can retain or discard a released/orphaned view without releasing a different current workspace's lease. Each decision is fenced by an immutable `0600` private snapshot. Changes to reviewed bytes supersede a pending review; changes after a completed discard require a new review before GC. Public events still contain only paths/key names/outcomes. Snapshots and incomplete snapshot staging are cleaned with their owning workspace or at startup.

V1 is not a same-UID process sandbox. A linked worktree necessarily exposes a writable common Git object database to normal Git commands, and a process that can both read a secret and run arbitrary Git plumbing can bypass attributes with commands such as `git hash-object -w --no-filters`. Git has no mandatory pre-object-write hook; a LaunchAgent runs as the login user; owner-controlled permissions and flags do not separate those processes. The clean filter is therefore an accidental-commit guardrail, not a security boundary against a malicious local actor. Shade will refuse to consume or publish a tree that tracks a private `.env*` name, but it does not re-read committed content at those boundaries, and it cannot identify the original pathname of an unreferenced blob written directly by that actor. An absolute information-flow guarantee would require removing raw Git access or introducing a broker under a distinct security principal, both outside the closed V1 assumptions.
